## 1단계: 프로젝트 뼈대

### D-001. 버전 정책: "패치가 한 번 이상 나온 최신 마이너"를 쓴다 (2026-11-25)

- **결정**: 각 제품의 최신 마이너 중 패치가 한 번 이상 나온 버전을 쓴다. 단, Java는 LTS를 쓴다.
- **선택지**
  - A. 무조건 최신 (Spring Boot 4.2.0, PostgreSQL 19.0, Redis 8.12.0, Kafka 4.4.0)
  - B. 패치가 한 번 이상 나온 최신 마이너 ← 선택
- **이유**
  - Spring Boot, PostgreSQL, Redis, Kafka는 OSS에서 LTS 개념이 없다. 그래서 "LTS"를 고를 수 없고 안정성 기준이 따로 필요했다.
  - `.0` 릴리스는 초기 버그 위험이 있고, 주변 라이브러리(Redisson 등)가 아직 따라오지 못했을 수 있다.
  - 원칙이 하나라서 버전마다 따로 설명할 필요가 없다.
- **확정 버전** (2026-11-25 Maven Central / Docker Hub 기준)

  | 항목 | 버전 | 비고 |
  |---|---|---|
  | Java | 25 (LTS) | Gradle 툴체인으로 고정 |
  | Spring Boot | 4.1.3 | 최신 4.2.0은 출시 6일째라 제외 |
  | Gradle | 9.9.2 | wrapper |
  | Testcontainers, Kafka 클라이언트, JDBC 드라이버 등 | Spring Boot BOM 관리 버전 | 직접 덮어쓰지 않는다 (Boot가 검증한 조합) |
  | Kafka (브로커) | apache/kafka:4.3.2 | 클라이언트(Boot 관리 4.2.x)보다 브로커가 새 버전인 것은 Kafka 호환 정책상 문제없음 |
  | PostgreSQL | 18.7 | |
  | Redis | 8.10.3 | |
  | Kafka UI | kafbat/kafka-ui:v1.5.1 | 기존 provectuslabs/kafka-ui는 2024년 이후 업데이트 없음 → 유지되는 포크 사용 |

### D-002. 빌드 도구: Gradle Kotlin DSL + 버전 카탈로그 (2026-11-25)

- **결정**: Gradle Kotlin DSL(`*.gradle.kts`)과 `gradle/libs.versions.toml`을 쓴다.
- **선택지**: Maven / Gradle Groovy DSL / Gradle Kotlin DSL ← 선택
- **이유**
  - 빌드 스크립트도 타입 체크와 IDE 자동완성을 받는다.
  - 멀티 모듈 공통 설정(Java 버전, 테스트 설정)을 루트 `subprojects {}` 한 곳에 둘 수 있다.
  - 버전 카탈로그에는 Spring Boot 버전만 고정하고, 나머지 라이브러리 버전은 Boot BOM(`platform(...)`)에 맡긴다.

### D-003. 실행 방식: Compose에는 인프라만, 서비스는 로컬 `bootRun` (2026-11-25)

- **결정**: `docker-compose.yml`에는 Kafka, Kafka UI, Redis, PostgreSQL 2개만 둔다. order-service와 stock-service는 `./gradlew :<모듈>:bootRun`으로 로컬에서 실행한다.
- **선택지**
  - A. 인프라만 Compose, 서비스는 로컬 실행 ← 선택
  - B. 서비스도 Docker 이미지로 만들어 Compose에 포함
- **이유**
  - 코드를 고친 뒤 이미지를 다시 빌드할 필요 없이 바로 다시 실행할 수 있다.
  - 동시성 실험 중에 디버거를 붙이거나 로그를 보기 쉽다.
  - 테스트는 어차피 Testcontainers로 인프라를 따로 띄우므로 Compose는 로컬 수동 확인용이다.
- **결과**: `bootRun`이 루트 `.env`를 읽어 환경 변수로 넘기도록 설정했다. Compose와 애플리케이션이 같은 `.env`를 공유한다.

### D-005. 서비스별 DB 분리: PostgreSQL 컨테이너 2개 (2026-11-25)

- **결정**: orderdb(호스트 포트 5433)와 stockdb(5434)를 별도 컨테이너로 띄운다.
- **이유**: 한 인스턴스에 스키마만 나누는 방식도 가능하다. 하지만 이 프로젝트의 핵심은 "두 서비스가 하나의 DB 트랜잭션으로 묶일 수 없다"는 조건이다. 그래서 인스턴스를 물리적으로 분리해 서비스가 상대 DB에 직접 접근할 여지를 없앴다.

## 2단계: stock-service 재고 도메인

### D-006. 재고 저장 구조: 재고 테이블 + 주문별 예약 테이블 (2026-11-25)

- **결정**: `stock(product_id, on_hand, reserved)`와 `stock_reservation(order_id UNIQUE, product_id, quantity, status)`를 함께 쓴다. 가용 재고는 `on_hand - reserved`로 계산한다.
- **선택지**
  - A. 재고 테이블 하나에 수량만 관리
  - B. 재고 테이블 + 예약 테이블 ← 선택
  - C. 입출고 원장(ledger)만 쌓고 합계로 계산
- **이유**
  - A는 "주문 X가 몇 개를 예약했는지"가 남지 않는다. 그래서 확정이나 복원 때 수량을 외부 입력에 의존해야 하고, 같은 주문의 중복 확정·복원을 막을 수 없다.
  - B는 예약 기록의 상태 전이(RESERVED에서만 확정·복원 가능)로 중복 처리를 막는다. `order_id UNIQUE`는 6단계 중복 소비 방지의 기반이 된다.
  - C는 재고를 확인할 때마다 합계를 내야 해서, 이 프로젝트의 중심인 "한 행에 대한 동시 갱신과 락 비교"와 맞지 않는다.
- **구현 메모**
  - StockReservation은 Stock과 `@ManyToOne`을 맺지 않고 `productId` 값만 가진다. 둘은 변경 이유가 다른 별도 단위이고, 함께 바꾸는 일은 서비스 트랜잭션이 맡는다.
  - DB에 `CHECK (reserved <= on_hand)`를 두었다. 이 제약은 마지막 방어선일 뿐이다. 두 트랜잭션이 같은 값을 읽고 덮어쓰는 lost update는 제약 위반 없이 일어나므로 막지 못한다. 3단계 실험에서 이 차이를 확인한다.

### D-007. 주문 한 건 = 상품 한 종류 (2026-11-25)

- **결정**: 주문은 상품 하나와 수량만 가진다.
- **선택지**: A. 단일 상품 ← 선택 / B. 여러 상품
- **이유**: 실험의 초점인 "한정 재고 한 상품에 주문이 몰리는 상황"이 선명하게 드러난다. 여러 상품이면 부분 예약 실패 처리와, 비관적 락에서 여러 행을 잠그는 순서에 따른 데드락까지 다뤄야 해서 범위가 커진다.

### D-008. "복원"은 예약 해제만 의미한다 (2026-11-25)

- **결정**: 복원(release)은 RESERVED → RELEASED 전이와 `reserved` 감소만 한다. 출고 확정된 예약은 되돌리지 않는다.
- **선택지**: A. 예약 해제만 ← 선택 / B. 출고 확정 후 반품 복원까지
- **이유**: 요구사항의 보상 처리(재고 부족 또는 주문 취소 → 예약 취소)와 정확히 맞는다. 반품 흐름은 범위 밖이다.

### D-009. 업무 규칙은 엔티티 메서드에 둔다 (2026-11-25)

- **결정**: `Stock.reserve/confirm/release`, `StockReservation.confirm/release`가 규칙을 직접 검사한다. `StockService`는 조회, 엔티티 메서드 호출, 트랜잭션 경계만 맡는다.
- **선택지**: A. 엔티티 메서드 ← 선택 / B. 서비스 계층(엔티티는 getter/setter만)
- **이유**: 규칙이 한 곳에 모이고, DB와 Spring 없이 순수 JUnit으로 빠르게 단위 테스트할 수 있다. setter를 열지 않아서 규칙을 우회한 상태 변경이 불가능하다.

### D-010. 스키마 관리: Flyway + `ddl-auto: validate` (2026-11-25)

- **결정**: 테이블은 `db/migration/V{n}__*.sql`로 만들고, Hibernate는 엔티티와 테이블이 일치하는지 검사만 한다.
- **선택지**: A. Flyway + validate ← 선택 / B. `ddl-auto: create`/`update`
- **이유**
  - UNIQUE, CHECK, FK 같은 제약을 SQL로 의도대로 통제할 수 있다.
  - 실험할 때마다 같은 스키마가 보장된다.
  - 매핑 실수(컬럼명, 타입)는 기동 시점에 바로 실패한다.
  - order-service는 테이블이 생기는 4단계에서 같은 방식으로 적용한다.

### D-011. JPA 기본 설정: OSIV 끄기, SEQUENCE ID (2026-11-25)

- **결정**: 두 서비스 모두 `spring.jpa.open-in-view: false`로 둔다. ID는 `GenerationType.SEQUENCE`(`allocationSize = 50`, DB 시퀀스 `INCREMENT BY 50`과 일치)로 생성한다.
- **이유**
  - **OSIV:** 기본값 true는 HTTP 응답이 끝날 때까지 DB 커넥션을 붙잡는다. 동시 요청 실험에서 커넥션 풀 고갈의 원인이 될 수 있고, 트랜잭션 경계를 서비스 계층으로 명확히 하는 편이 좋다.
  - **SEQUENCE:** IDENTITY는 INSERT를 실행해야 ID를 알 수 있어서 Hibernate가 배치 INSERT를 하지 못한다. SEQUENCE는 ID를 50개씩 미리 받아 와서 시퀀스 호출을 줄이고 배치도 가능하다.

## 3단계: 실험 1 (락 방식 4종 비교)

### D-012. 4가지 방식의 공존: 같은 테이블에 엔티티 2개 + 전략 인터페이스 (2026-11-25)

- **결정**
  - 재고 규칙은 `@MappedSuperclass AbstractStock`에 둔다.
  - `Stock`(version 없음)과 `VersionedStock`(`@Version`)이 같은 `stock` 테이블을 매핑한다.
  - 방식별로 `StockReservationStrategy` 구현체 4개를 둔다: 락 없음, 낙관적 락, 비관적 락, Redis 분산 락.
- **선택지**
  - A. 같은 테이블에 엔티티 2개 + 전략 인터페이스 ← 선택
  - B. `Stock`에 `@Version`을 붙이고, 락 없음은 JPQL UPDATE로 우회
  - C. 방식마다 코드를 바꿔 커밋하고 각각 측정
- **이유**
  - `Stock`에 `@Version`을 붙이면 모든 UPDATE에 버전 조건이 붙어서 "락 없음" 기준선이 사라진다.
  - B는 락 없음 경로가 엔티티 규칙을 거치지 않아 비교가 불공정하다.
  - C는 실험을 다시 돌리기 어렵다.
  - A는 네 방식을 같은 규칙, 같은 테스트, 같은 조건에서 언제든 다시 실행할 수 있다.
- **결과**
  - `version` 컬럼은 Flyway V3로 추가했다(기본값 0). `Stock`은 이 컬럼을 매핑하지 않는다.
  - 모든 전략이 같은 계약을 지키는지 `StockReservationStrategyContractTest`가 검증한다. 전략 빈을 추가하면 자동으로 검증 대상이 된다.

### D-013. 낙관적 락 재시도: 트랜잭션 바깥에서 최대 10회, 10~50ms 무작위 대기 (2026-11-25)

- **결정**: 충돌(`OptimisticLockingFailureException`)이 나면 `TransactionTemplate`으로 새 트랜잭션을 열어 재시도한다. 최대 10회, 시도 사이에 10~50ms 무작위 대기를 둔다. 10회를 넘기면 `ReservationRetryExhaustedException`을 던진다.
- **선택지**: A. 재시도 없음 / B. 제한 횟수 + 대기 ← 선택 / C. 무한 재시도
- **이유**
  - A는 재고가 남았는데도 대부분 실패한다(과소 판매).
  - C는 처리 시간에 상한이 없다.
  - 재시도를 트랜잭션 안에서 하면, 롤백 전용 상태와 영속성 컨텍스트에 남은 옛 version 때문에 계속 실패한다. 그래서 바깥에서 매번 새로 읽는다.
  - 대기 시간을 무작위로 하는 이유: 모두가 같은 간격으로 재시도하면 다시 동시에 부딪힌다.
  - Spring Framework 7의 `@Retryable` 대신 루프를 직접 작성했다. 트랜잭션 경계가 코드에 드러나게 하기 위해서다.
- **결과**: 충돌은 약 500회 일어났지만 재시도 소진은 0이었다(실험 1).

### D-014. Redis 분산 락: Redisson RLock 4.6.1 (2026-11-25)

- **결정**: Redisson `RLock`을 쓴다. 락 키는 상품 단위(`lock:stock:{productId}`), 대기 시간은 30초, leaseTime은 생략한다(watchdog이 만료를 관리).
- **선택지**: A. Redisson ← 선택 / B. Lettuce로 `SET NX PX` 스핀 락 직접 구현 / C. 둘 다
- **이유**
  - Redisson은 Pub/Sub으로 해제 알림을 받아 대기한다. 반복 조회로 Redis에 부하를 주지 않는다.
  - watchdog이 작업 중 락 만료를 막고, 프로세스가 죽으면 연장이 멈춰 자동으로 해제된다.
  - 락 값에 소유자(클라이언트 ID와 스레드 ID)가 들어가 다른 스레드가 잘못 해제할 수 없다.
  - B는 원리를 보여주지만 이 문제들을 직접 다뤄야 한다. C는 범위가 커진다.
- **버전**: D-001 원칙(패치가 한 번 이상 나온 최신 마이너)에 따라 4.6.1을 쓴다(4.7.0, 4.8.0은 패치 없음). Spring Boot BOM이 관리하지 않으므로 버전 카탈로그에 직접 고정했다.
- **대기 시간 30초인 이유**: 1,000건이 한 줄로 서도 타임아웃이 나지 않게 해서, 타임아웃 실패가 결과에 섞이지 않게 했다.

### D-015. 분산 락과 트랜잭션 순서: 락 획득 → 트랜잭션 → 커밋 → 락 해제 (2026-11-25)

- **결정**
  - 분산 락 전략 메서드에는 `@Transactional`을 붙이지 않는다.
  - 락 안에서 `@Transactional` 메서드(`StockService.reserve`)를 프록시를 통해 호출한다.
  - 커밋이 끝난 뒤 `finally`에서 락을 해제한다.
- **선택지**: A. 올바른 순서만 구현하고 잘못된 순서는 문서로 설명 ← 선택 / B. 잘못된 순서도 변형으로 구현해 측정
- **이유**
  - 락을 트랜잭션 안에서 해제하면 커밋 전에 락이 풀린다. 그 틈에 다음 요청이 커밋 전의 옛 값을 읽어 초과 판매가 생긴다.
  - B는 이를 숫자로 보여줄 수 있지만 범위를 지키기 위해 A로 했다.

### D-016. 측정 방법: JUnit + Testcontainers, 서비스 직접 호출 (2026-11-25)

- **결정**
  - 스레드 100개 풀에 요청 1,000건을 넣고 `CountDownLatch`로 동시에 출발시킨다.
  - 방식마다 예열 1회 후 5회 측정해 중앙값과 최소~최대를 기록한다.
  - DB 커넥션 풀은 Boot 기본값 10을 그대로 쓴다.
  - 실험은 `@Tag("experiment")`로 일반 `test`에서 빼고 `./gradlew :stock-service:experiment`로만 실행한다.
  - 낙관적 락 충돌 횟수는 실험에서만 Hibernate 통계를 켜서 센다.
- **선택지**: A. JUnit + Testcontainers ← 선택 / B. HTTP API + 부하 도구(k6 등)
- **이유**: API와 도구를 추가하지 않고도 같은 조건을 누구나 한 줄 명령으로 재현할 수 있다. HTTP 계층을 빼서 순수하게 락 방식의 차이만 볼 수 있다.

### D-017. 비관적 락은 타임아웃 없이 대기 (2026-11-25)

- **결정**: `PESSIMISTIC_WRITE`에 락 타임아웃을 두지 않는다.
- **선택지**: A. 타임아웃 없음 ← 선택 / B. `jakarta.persistence.lock.timeout` 3초
- **이유**: 실험에서는 모든 요청이 결국 처리되므로, 타임아웃 실패가 섞이지 않은 순수한 대기 비용을 본다.
- **주의**: 실무에서는 타임아웃이 필요하다. 락을 쥔 트랜잭션이 느려지면 대기자들이 커넥션을 붙잡은 채 쌓여 커넥션 풀이 고갈되기 때문이다.
- **확인한 사실**: Hibernate 7 + PostgreSQL에서 `PESSIMISTIC_WRITE`는 `FOR UPDATE`가 아니라 `FOR NO KEY UPDATE`로 실행된다. 이 락은 FK 검사가 거는 `KEY SHARE` 락과 충돌하지 않는다. 그래서 예약 INSERT의 FK 검사가 재고 행 락을 기다리지 않는다.

## 4단계: order-service 주문 API와 Redis 멱등 키

### D-018. 멱등 키는 클라이언트가 `Idempotency-Key` 헤더로 보낸다 (2026-11-25)

- **결정**: 주문 요청마다 클라이언트가 고유한 키(UUID 등)를 `Idempotency-Key` 헤더에 담는다. 응답을 받지 못해 재시도할 때는 같은 키를 다시 보낸다.
- **선택지**: A. 클라이언트 헤더 ← 선택 / B. 서버가 요청 내용 해시로 키 생성
- **이유**
  - IETF 표준 초안(`Idempotency-Key` HTTP 헤더)이고, Stripe 같은 결제 API가 쓰는 방식이다.
  - B는 "사용자가 같은 상품을 정말로 두 번 주문"한 경우와 "네트워크 재시도"를 구분할 수 없다.

### D-019. 2단 방어: Redis 멱등 키(1차) + DB UNIQUE 제약(최종) (2026-11-25)

- **결정**
  - Redis에 `SET NX EX`로 키를 "처리 중"으로 선점한다.
  - 주문을 저장하고 커밋한 뒤, 키에 "완료 + 주문 ID"를 기록한다.
  - 처리 중인 키로 요청이 오면 409, 완료된 키로 오면 저장된 주문을 다시 돌려준다(201, `Idempotent-Replayed: true`).
  - 저장에 실패하면 내가 선점한 키만 Lua 스크립트로 지워 재시도를 허용한다.
  - 최종 방어선은 `orders.idempotency_key UNIQUE` 제약이다.
- **선택지**
  - A. Redis 선점 + 결과 저장
  - B. Redis 선점만, 중복이면 409
  - C. DB UNIQUE 제약만
  - D. A + DB UNIQUE ← 선택
- **이유**
  - Redis는 대부분의 중복을 DB까지 보내지 않고 빠르게 걸러낸다.
  - Redis와 DB는 하나의 트랜잭션으로 묶을 수 없다. 키가 만료되거나 유실될 수 있고, 선점 후 커밋 전에 서버가 죽을 수도 있으며, Redis 자체에 장애가 날 수도 있다. 이런 경우에도 DB 제약이 중복 주문 저장을 막는다.
  - "완료" 기록은 반드시 커밋 후에 한다. 커밋 전에 쓰면, 커밋이 실패했을 때 존재하지 않는 주문을 재요청에 돌려주게 된다.
- **결과**
  - 같은 키로 동시에 10건을 보내면 주문 1건이 저장되고, 나머지는 409(처리 중)를 받았다.
  - Redis 키를 지운 뒤 재요청해도 DB 제약으로 같은 주문 ID가 돌아왔다.

### D-020. 같은 키로 다른 내용이 오면 422로 거절한다 (2026-11-25)

- **결정**: 요청 내용(`productId`, `quantity`)의 SHA-256 지문을 Redis 값과 `orders.request_fingerprint`에 함께 저장한다. 같은 키인데 지문이 다르면 422 Unprocessable Content로 거절한다.
- **선택지**: A. 지문 비교 후 422 ← 선택 / B. 키만 보고 처음 결과 반환
- **이유**
  - B는 클라이언트가 키를 잘못 재사용하면, 다른 상품을 주문했는데 이전 주문 결과를 받게 된다.
  - 지문을 DB에도 저장하므로 Redis 키가 사라진 뒤에도 거절할 수 있다.

### D-021. 멱등 처리는 주문 서비스 계층에서 명시적으로 한다 (2026-11-25)

- **결정**: `OrderService.placeOrder`가 키 선점 → 저장 → 완료 기록 흐름을 직접 수행한다.
- **선택지**: A. Filter/Interceptor / B. 서비스 계층 ← 선택 / C. `@Idempotent` AOP
- **이유**
  - API가 하나라 공통화할 이득이 적다.
  - 흐름이 코드에 그대로 보이고, 트랜잭션 경계(커밋 후 완료 기록)를 명확히 둘 수 있다.
  - Filter 방식은 요청 본문을 읽고 응답을 저장하는 처리가 복잡하다.

### D-022. API 형태와 에러 형식 (2026-11-25)

- **결정**
  - `POST /orders` (헤더 `Idempotency-Key`, 본문 `{productId, quantity}`)는 201과 `Location`, `Idempotent-Replayed` 헤더를 돌려준다.
  - `GET /orders/{id}`로 주문을 조회한다.
  - 새 주문은 `PENDING`으로 저장한다(상태 전이는 5단계).
  - 에러는 RFC 9457 `ProblemDetail`(`application/problem+json`)로 통일한다: 400 검증 실패·헤더 누락, 404, 409(`Retry-After: 1`), 422.
- **이유**: 표준 형식이라 클라이언트가 에러를 일관되게 처리할 수 있다. 재생 여부를 헤더로 알려 주면 클라이언트가 새 주문인지 재요청 결과인지 구분할 수 있다.

### D-023. 멱등 키 TTL과 Redis 장애 시 동작 (2026-11-25)

- **결정**
  - **TTL:** 처리 중 30초, 완료 24시간.
  - **Redis 장애 시:** Redis 호출이 실패하면 주문을 막지 않고(fail-open) DB 제약만으로 처리한다. 완료 기록과 해제가 실패해도 이미 커밋된 주문은 성공으로 응답한다.
- **이유**
  - 처리 중 TTL을 짧게 두는 이유: 서버가 처리 중에 죽어도 30초 뒤에는 같은 키로 재시도할 수 있다.
  - 완료 TTL 24시간은 클라이언트 재시도 창으로 충분하다. 그 이후의 재요청은 DB 제약이 막는다.
  - Redis는 멱등성의 "빠른 경로"일 뿐이다. DB 제약이 정합성을 보장하므로, Redis 장애 때문에 주문 기능 전체를 멈출 이유가 없다.
- **확인**: `OrderServiceRedisDownTest`에서 Redis 장애를 가정해도 주문이 저장되고, 같은 키의 재요청은 DB 제약으로 같은 주문을 돌려받는 것을 검증했다.

### D-024. 재고 예약에는 비관적 락을 쓴다 (2026-11-26)

- **결정**
  - 실제 주문 흐름(5단계 Kafka 소비자)의 재고 예약은 `PessimisticLockStockReservationStrategy`를 쓴다. 이 전략은 `SELECT ... FOR NO KEY UPDATE`로 재고 행을 잠근다.
  - 나머지 세 전략은 실험 재현용으로 코드에 남긴다.
- **근거: 실험 1 결과** ([GitHub 러너 run #1](https://github.com/hbyun94/order-stock-consistency/actions/runs/45742635619), 재고 100, 동시 요청 1,000, 스레드 100, 커넥션 풀 10, 5회 중앙값)

  | 방식 | 초과 판매 | 낙관적 락 충돌 | 재시도 소진 | 처리 시간(ms) |
  |---|---|---|---|---|
  | 락 없음 | 795 (766~889) | 0 | 0 | 699 (585~728) |
  | 낙관적 락 | 0 | 663 (638~687) | 0 (0~1) | 621 (582~747) |
  | **비관적 락** | **0** | 0 | 0 | **283 (249~306)** |
  | Redis 분산 락 | 0 | 0 | 0 | 848 (822~1043) |

- **선택지와 판단**
  - **비관적 락 ← 선택.**
    - 정합성을 지키는 세 방식 중 가장 빠르다(283ms).
    - 줄을 세워 처리하므로 버려지는 작업이 없다.
    - 한정 재고처럼 한 행에 경합이 몰리는 상황에 맞다.
    - 동작이 단순해서 설명하고 운영하기 쉽다.
  - **낙관적 락**
    - 충돌이 성공 1건당 약 6.6회 일어나 2배 이상 느렸다.
    - 재시도 소진(1건)이 나와서 과소 판매 위험도 확인됐다.
    - 경합이 드물 때 유리한 방식이라 이 시나리오에는 맞지 않는다.
  - **Redis 분산 락**
    - Redis 왕복 비용 때문에 가장 느렸다(약 3배).
    - 보호 대상이 DB 행 하나인 이 시나리오에서는, 락 대기 중 DB 커넥션을 쓰지 않는다는 장점보다 새 장애 지점이 생기는 비용이 크다.
- **조건과 후속 작업**
  - **락 대기 타임아웃:** 실험에서는 순수 대기 비용을 보려고 타임아웃을 두지 않았다(D-017). 실제 흐름에 적용할 때는 타임아웃을 둔다. 락을 쥔 트랜잭션이 느려지면 대기자들이 커넥션을 붙잡은 채 쌓이기 때문이다. 값과 타임아웃 시 처리(재시도 여부)는 5단계 구현 때 정한다.
  - **5단계 토픽 설계와의 관계:** Kafka 메시지 키를 상품 ID로 하면 같은 상품의 이벤트가 한 파티션, 한 소비자로 순서대로 처리되어 DB 경합 자체가 줄어든다. 그래도 리밸런싱 중 중복 처리, 여러 인스턴스, 확정·복원 같은 다른 경로와의 동시 실행이 있으므로 락은 유지한다.
- **측정 환경 메모**
  - 개발용 클라우드 컨테이너에서는 낙관적 락과 비관적 락의 차이가 오차 범위로 보였다(세 번 실행하는 동안 순위가 바뀜).
  - 재현 가능한 GitHub 러너 결과를 결정의 기준으로 삼았다. 자세한 내용은 README "한계와 측정 환경 차이"에 있다.

## 5단계: Kafka 이벤트 흐름

```
POST /orders → 주문 저장(PENDING) → [order.created] → stock-service 재고 예약(비관적 락)
   ├ 성공 → [stock.reserved]            → order-service: 주문 RESERVED
   └ 실패 → [stock.reservation-failed]  → order-service: 주문 CANCELLED (보상)
```

### D-025. 주문 이벤트는 커밋 후 발행한다 (2026-11-26)

- **결정**: `OrderService`가 트랜잭션 안에서 Spring 내부 이벤트(`OrderPlacedEvent`)를 발행하고, `@TransactionalEventListener(AFTER_COMMIT)`가 커밋 후 Kafka로 `order.created`를 보낸다.
- **선택지**: A. 커밋 후 발행 ← 선택 / B. 트랜잭션 안에서 발행 / C. 바로 Outbox
- **이유**
  - B는 롤백된 주문의 이벤트가 이미 나가 버리는 "유령 이벤트"를 만든다.
  - A는 그 문제는 없지만, 커밋 후 전송이 실패하면 이벤트가 유실되어 주문이 PENDING에 멈춘다.
  - 이 약점은 의도적으로 남긴다. 실험 3에서 재현하고 7단계 Outbox로 해결하는 과정을 보여 주기 위해서다. C로 바로 가면 그 기준선이 사라진다.
- **구현 메모**
  - 커밋 후 리스너에서 예외를 던져도 주문은 되돌릴 수 없다. 그래서 전송 실패는 로그로 남기고 요청은 성공으로 응답한다.
  - 브로커에 닿지 못할 때 `send()`가 요청 스레드를 오래 붙잡지 않도록 `max.block.ms`를 5초로 줄였다(기본 60초).

### D-026. 토픽은 이벤트 종류별로 나눈다 (2026-11-26)

- **결정**: `order.created`, `stock.reserved`, `stock.reservation-failed`
- **선택지**: A. 이벤트 종류별 토픽 ← 선택 / B. 도메인별 토픽(`order-events`, `stock-events`) + 타입 헤더
- **이유**: 소비자가 필요한 토픽만 구독하고, 토픽마다 메시지 형식이 하나라 명확하다. B의 장점인 "같은 주문의 여러 이벤트 간 순서 보장"은 주문당 결과 이벤트가 하나인 이 흐름에서는 이점이 작다.

### D-027. 메시지 키: order.created는 상품 ID, 결과 이벤트는 주문 ID (2026-11-26)

- **결정**: `order.created`의 키는 상품 ID로 한다. `stock.reserved`와 `stock.reservation-failed`의 키는 주문 ID로 한다.
- **선택지**: A. order.created는 상품 ID, 결과는 주문 ID ← 선택 / B. 모두 주문 ID
- **이유**
  - 같은 상품의 주문이 한 파티션에 모여 한 소비자가 순서대로 처리한다. 어차피 DB 행 락에서 한 줄로 서야 하는 작업(D-024)을 Kafka 단계에서 미리 줄 세우는 셈이라, 락 대기와 커넥션 점유가 줄어든다.
  - 비관적 락은 리밸런싱, 여러 인스턴스, 다른 경로(확정·복원)와 동시에 실행될 때를 대비한 안전망으로 유지한다.
- **대가**: 인기 상품 하나의 처리량은 소비자 스레드 하나로 제한된다(핫 파티션).

### D-028. 이벤트 계약은 서비스마다 각자 record로 정의하고 JSON 필드로 맞춘다 (2026-11-26)

- **결정**
  - 공유 모듈을 두지 않는다. 각 서비스의 `messaging` 패키지에 같은 이름과 필드를 가진 record를 둔다.
  - 보내는 쪽은 `JacksonJsonSerializer`를 쓰되 타입 헤더(`__TypeId__`)를 끈다.
  - 받는 쪽은 문자열로 받은 뒤, `StringJacksonJsonMessageConverter`가 `@KafkaListener` 메서드의 파라미터 타입으로 변환한다.
- **선택지**: A. 공유 모듈(`event-contract`) / B. 서비스별 record + JSON 필드 ← 선택 / C. Avro + Schema Registry
- **이유**
  - A는 두 서비스가 같은 jar 버전에 묶여 독립 배포가 어려워진다.
  - C는 인프라가 늘어나 범위 밖이다.
  - 타입 헤더를 끄면 받는 쪽이 보내는 쪽의 패키지와 클래스 이름을 몰라도 된다.
  - 계약은 각 서비스 테스트가 상대 서비스 대신 같은 JSON을 직접 주고받으며 검증한다. 상대 서비스의 record를 쓰지 않고 자기 record로 보낸다.

### D-029. stock-service는 예약 커밋 후 결과 이벤트를 보내고, 브로커 확인까지 기다린다 (2026-11-26)

- **결정**
  - 소비자는 다음 순서로 처리한다: 예약(`@Transactional`, 커밋) → 결과 이벤트 전송 → 브로커 확인(`get`, 10초) → 정상 종료 → 오프셋 커밋.
  - 전송이 실패하면 예외를 던져 같은 메시지를 다시 처리하게 한다.
- **선택지**: A. 커밋 후 발행 ← 선택 / B. Kafka 트랜잭션(consume-process-produce)
- **이유**: B는 Kafka 안에서는 정확히 한 번 처리를 보장하지만 DB 커밋과는 묶이지 않아 이 문제의 해법이 되지 못한다.
- **알려진 약점**
  - 예약 커밋 후 전송이 실패해 다시 처리하면, 같은 주문을 또 예약하려다 `order_id UNIQUE`에 막혀 계속 실패한다. 이 중복 처리 문제는 6단계에서 다룬다.
  - 결과 이벤트 유실 문제는 7단계(Outbox)에서 다룬다.

## 6단계: 중복 소비 (실험 2)

### D-033. stock-service는 주문별 처리 결과를 기록하고, 중복이면 기록된 결과를 다시 보낸다 (2026-11-26)

- **결정**
  - `order_event_result(order_id PK, product_id, quantity, outcome, reason)` 테이블을 둔다.
  - `order.created` 한 건에 대한 결정(예약 성공, 또는 재고 부족·미등록 상품으로 거절)을 재고 변경과 **같은 트랜잭션**에서 한 번만 기록한다.
  - 같은 주문이 다시 오면 새로 판단하지 않고, 기록된 결정으로 같은 결과 이벤트를 다시 보낸다.
- **선택지**
  - A. 기존 예약 기록(`stock_reservation.order_id`)으로 판단
  - B. 처리 결과 테이블 ← 선택
  - C. 이벤트 ID 기반 범용 중복 제거 테이블
  - D. Redis에 처리한 키 기록
- **이유**
  - A는 거절된 주문에 기록이 남지 않아서, 재고가 풀린 뒤 다시 오면 예약된다(재고 누수, 실험 2 ③).
  - C는 같은 주문의 이벤트가 새 ID로 다시 만들어지면 막지 못한다(예: 7단계 Outbox의 재발행). 비즈니스 키(주문 ID)가 더 강한 기준이다.
  - D는 DB 트랜잭션과 원자적으로 묶이지 않는다.
- **중복 방지 장치 세 겹**
  1. 처리 전에 기록을 조회한다.
  2. 재고 행 락(D-024)을 얻은 뒤 기록을 다시 조회한다. 같은 상품의 동시 처리는 락에서 줄을 서므로, 앞선 처리가 커밋한 기록이 여기서 보인다.
  3. `order_id` PK. 잠글 행이 없는 미등록 상품의 동시 처리도 여기서 막힌다. 진 쪽은 롤백하고 이긴 쪽의 기록을 읽는다.
- **구현 메모**
  - **`Persistable` 구현:** ID를 직접 넣는 엔티티를 Spring Data `save()`에 넘기면 merge로 처리되어, 같은 ID의 행이 있으면 조용히 덮어쓴다(UPDATE). 그래서 `Persistable.isNew()`로 항상 INSERT하게 해서, 중복이 PK 위반으로 드러나게 했다.
  - **재고 부족을 도메인 메서드에서 잡는 이유:** 트랜잭션 프록시(`@Transactional` 메서드)를 거쳐 예외가 나가면 같은 트랜잭션이 rollback-only가 되어 거절 기록까지 롤백된다. 그래서 프록시가 아닌 도메인 메서드(`Stock.reserve`)에서 재고 부족을 잡는다.
  - **실제 흐름의 락:** 실제 흐름은 더 이상 `PessimisticLockStockReservationStrategy`를 거치지 않는다. 대신 같은 비관적 락 쿼리(`findByProductIdForUpdate`)를 이 서비스에서 직접 쓴다. 전략 클래스들은 실험 1 재현용으로 남는다. D-024의 결정(비관적 락)은 그대로다.
- **결과(실험 2)**
  - 중복 전달, 결과 전송 실패 후 재전달, 거절 후 재전달의 세 시나리오 모두에서 재고 차감은 1번이었다.
  - 결과 이벤트도 모두 도달했고, 재고 누수는 0이었다.
  - 5단계 방식에서는 결과 전송 실패 후 재전달이 10번 모두 실패해, 결과가 한 번도 나가지 않았다(주문 PENDING 고정).

### D-034. order-service는 상태 기반으로 결과 이벤트를 멱등 처리한다 (2026-11-26)

## 7단계: Transactional Outbox (실험 3)

### D-036. 두 서비스 모두 Transactional Outbox로 이벤트를 발행한다 (2026-11-26)

- **결정**
  - **order-service:** 주문과 `order.created` 이벤트를 한 트랜잭션에 저장한다.
  - **stock-service:** 예약 결정과 결정 기록, 결과 이벤트(`stock.reserved`, `stock.reservation-failed`)를 한 트랜잭션에 저장한다.
  - 저장 위치는 각 서비스의 `outbox_event` 테이블이다.
  - 애플리케이션 계층은 `OrderEvents`와 `ReservationResultEvents` 인터페이스에만 의존하고, Outbox 구현은 messaging 계층이 맡는다.
  - 구현 메서드는 `@Transactional(MANDATORY)`이다. 트랜잭션 밖에서 호출하면 예외가 나서, 업무 데이터와 따로 커밋되는 실수를 막는다.
- **선택지**: A. order-service만 / B. 두 서비스 모두 ← 선택
- **이유**
  - stock-service에도 같은 구멍이 있었다. Spring Kafka 기본 재시도는 대기 없이 10번이라, 브로커가 몇 초만 끊겨도 재시도가 소진되고 결과가 유실된다.
  - 결과 이벤트를 결정과 같은 트랜잭션에 두면 소비자는 커밋만 하면 되고, 전송을 기다릴 필요가 없다.
- **대체한 결정**
  - D-025(커밋 후 직접 발행)를 대체한다. 기존 `OrderCreatedPublisher`는 삭제했고, 비교용 기준선은 실험 3 테스트에만 남겼다.
  - D-029(stock 결과 전송 후 대기)를 대체한다.
- **직렬화 메모 (D-028 보완)**
  - Outbox 행에는 저장 시점에 직렬화한 JSON 문자열이 들어간다.
  - 발행기는 그 문자열을 그대로 보내도록, 값 직렬화를 `StringSerializer`로 바꾼 전용 `KafkaTemplate`을 내부에서 만들어 쓴다.
  - 이 템플릿을 빈으로 등록하지 않은 이유: `KafkaTemplate` 빈이 하나라도 있으면 Boot가 기본 `KafkaTemplate`을 만들지 않는다. 처음에 빈으로 등록했다가 기존 기능이 깨지는 것을 테스트로 확인했다.
  - JSONB는 저장할 때 공백을 정규화하므로, 테스트에서는 문자열 비교 대신 JSON을 파싱해서 비교한다.

### D-037. 발행기는 500ms 주기의 폴링 방식이다 (2026-11-26)

- **결정**
  - `@Scheduled(fixedDelay)`로 500ms마다 미발행 행을 최대 100개 가져와 순서대로 보낸다.
  - 브로커 확인을 기다린 뒤(최대 5초) `published_at`을 기록한다.
  - 전송이 실패하면 `attempts`와 `last_error`를 기록하고 그 주기를 멈춘다. 다음 주기에 같은 행부터 다시 보낸다.
- **선택지**: A. 폴링 ← 선택 / B. CDC(Debezium) / C. 즉시 전송 + 폴링 보완
- **이유**
  - 인프라를 추가하지 않고, 동작이 코드에 그대로 드러난다.
  - 대가는 발행 지연이다. 실험 3 정상 시나리오에서 평균 약 350ms였다.
  - CDC는 지연이 거의 없지만 Kafka Connect와 Debezium이 추가되어 범위 밖이다.
- **최소 한 번 발행**: 전송은 성공했는데 `published_at` 커밋 전에 죽으면 다시 보낸다. 이 중복은 소비자의 멱등 처리(D-033, D-034)가 받아낸다.

### D-038. 여러 발행기는 `FOR UPDATE SKIP LOCKED`로 행을 나눠 잡는다 (2026-11-26)

- **결정**: 발행기는 `SELECT … WHERE published_at IS NULL ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED`로 행을 잠근 채 보낸다.
- **선택지**: A. SKIP LOCKED ← 선택 / B. ShedLock 등 분산 스케줄 락 / C. 단일 인스턴스 가정
- **이유**
  - 다른 발행기가 이미 잠근 행은 기다리지 않고 건너뛰므로, 같은 행을 동시에 두 번 보내지 않고 인스턴스끼리 일을 나눈다.
  - PostgreSQL 기능만으로 된다.
  - 미발행 행만 담는 부분 인덱스(`WHERE published_at IS NULL`)로 조회를 작게 유지한다.
- **검증**: 한 트랜잭션이 행을 잠근 동안 다른 트랜잭션의 같은 쿼리가 0건을 받는 것을 테스트로 확인했다(`OutboxRelayTest.skipLocked`).
- **대가**
  - 전송하는 동안 해당 행의 락을 쥐고 있다(최대 5초).
  - 여러 인스턴스가 서로 다른 행을 동시에 보내면 행 사이의 발행 순서는 보장되지 않는다. 이 흐름의 이벤트는 주문마다 독립이라 문제가 되지 않는다.

### D-039. 중복 소비 시 결과 이벤트를 다시 만들지 않는다 (D-033 일부 변경) (2026-11-26)

  - 이제 첫 결정의 결과 이벤트가 같은 트랜잭션으로 Outbox에 저장되어 발행이 보장되므로, 재발행은 중복 메시지만 늘린다.

  - 리스너의 직접 재전송을 전제로 한 `OrderCreatedRedeliveryTest`는 같은 의도(결과 전송 실패에도 유실 없음, 재고 1회 차감)를 실제 브로커 장애로 검증하는 `ResultEventOutageTest`로 대체했다.

### D-040. 발행 완료된 Outbox 행은 지우지 않고 `published_at`만 기록한다 (2026-11-26)

### D-041. 실험 3은 실제 브로커 장애로 재현하고 일반 테스트로 실행한다 (2026-11-26)

- **결정**
  - Testcontainers Kafka 컨테이너를 실제로 6초 일시정지(`docker pause`)해 브로커 장애를 만든다.
  - "커밋 직후 프로세스 종료"는 전송 단계를 건너뛰는 것으로 흉내 낸다.
  - 5단계 방식(직접 전송)은 테스트 소스에만 기준선으로 둔다.
  - 일반 `test`에 포함한다(약 1분).
- **선택지**: 기준선 위치 A. 테스트 소스 ← 선택 / B. 운영 코드에 설정으로 공존. 실행 방식 A. 일반 테스트 ← 선택 / B. 수동 워크플로
- **실험 조건 메모**
  - 프로듀서 전송 제한 시간을 3초로 줄였다(기본 120초). "장애가 전송 제한 시간보다 길다"는 조건을 짧은 시간에 만들기 위해서다.
  - 제한 시간이 기본값이어도 장애가 2분을 넘기면 같은 유실이 생긴다.
- **결과**
  - 직접 전송의 유실은 3회 실행에서 28~32건이었다(장애 8~12건, 커밋 직후 종료 20건).
  - Outbox의 유실은 0건이었다.
  - 직접 전송은 장애 중 20건 모두를 "실패"로 보고했지만 일부는 실제로 도착했다. 타임아웃은 "실패"가 아니라 "모름"이다.

### D-042. 리스너 실패는 같은 자리에서 재시도한다 (블로킹 재시도) (2026-11-27)

- **결정**: 두 서비스 모두 `DefaultErrorHandler`로 실패한 메시지를 그 자리에서 다시 처리한다. 재시도 토픽은 쓰지 않는다.
- **선택지**: A. 같은 자리 재시도 ← 선택 / B. 재시도 토픽(`@RetryableTopic`)
- **이유**
  - `order.created`의 키는 상품 ID라서 같은 상품의 주문이 한 파티션에 순서대로 쌓인다. 한정 재고에서는 이 순서가 "먼저 온 주문이 먼저 재고를 받는다"는 공정성과 같다.
  - 재시도 토픽은 실패한 메시지를 옆으로 빼고 뒤 메시지를 먼저 처리하므로, 늦게 온 주문이 재고를 먼저 가져갈 수 있다.
  - 재시도 단계마다 토픽이 생겨 운영 대상이 늘어난다.
- **비용**: 재시도하는 동안(최대 약 15초) 같은 파티션의 뒤 메시지가 기다린다. 테스트에서 이 순서 유지를 확인했다.

### D-043. 재시도는 지수 백오프로 4회(총 5번 시도, 약 15초)다 (2026-11-27)

- **결정**: 간격 1초에서 시작해 2배씩 늘리고 최대 8초로 제한한다(1s → 2s → 4s → 8s). 값은 `kafka.retry.*` 설정으로 둔다.
- **선택지**: A. 횟수 제한 후 DLT ← 선택 / B. 일시 장애는 무한 재시도
- **이유**
  - DB 순단, 락 대기 초과(D-047) 같은 일시 장애는 대개 수 초 안에 풀린다.
  - 총 대기가 폴링 제한(`max.poll.interval.ms`, 기본 5분)보다 훨씬 짧아 리밸런싱을 일으키지 않는다.
  - 무한 재시도는 메시지를 잃지 않지만, 장애가 길어지면 소비 전체가 멈춘다.
- **비용**: 장애가 15초를 넘기면 그동안의 메시지가 DLT로 간다. 재처리가 필요하다(D-046).
- **구현 메모**: 테스트는 시간을 줄이려고 간격만 100ms~400ms로 바꾸고, 횟수는 운영과 같은 4회로 검증한다.

### D-044. 다시 해도 같은 실패는 재시도하지 않고 바로 DLT로 보낸다 (2026-11-27)

- **결정**
  - 깨진 JSON(메시지 변환 실패): Spring Kafka가 기본으로 재시도 대상에서 뺀다.
  - 필수 값 누락: 리스너가 검사해 `InvalidEventException`을 던진다(주문 ID·상품 ID 없음, 수량 0 이하).
  - 없는 주문(order-service): `OrderNotFoundException`. 주문은 이벤트보다 먼저 커밋되므로(Outbox, D-036) 기다려도 생기지 않는다.
- **이유**: 재시도해 봐야 결과가 같아서, 15초 동안 파티션만 막는다.

### D-045. DLT는 `<원래 토픽>.dlt`, 같은 파티션, 원문 그대로다 (2026-11-27)

- **결정**
  - 이름: `order.created.dlt`, `stock.reserved.dlt`, `stock.reservation-failed.dlt`. 기존 토픽의 점 표기를 따른다.
  - 원래 파티션 번호로 보낸다. 그래서 DLT의 파티션 수를 원래 토픽과 같은 3개로 코드에서 선언한다.
  - 값은 받은 문자열(JSON 원문)을 그대로 보낸다. 실패 원인(예외 클래스, 메시지)과 원래 토픽·파티션·오프셋은 Spring Kafka가 헤더에 남긴다.
  - DLT 전송이 실패하면 오프셋을 커밋하지 않고 같은 메시지를 다시 처리한다. 메시지가 사라지지 않는다.
- **구현 메모**
  - DLT 전송용 `KafkaTemplate`은 값 직렬화기를 문자열로 바꿔 내부에서 만든다. 기본 템플릿의 JSON 직렬화기는 문자열을 따옴표로 한 번 더 감싸기 때문이다.
  - 빈으로 등록하지 않는다. OutboxRelay와 같은 이유로, `KafkaTemplate` 빈이 생기면 Boot가 기본 템플릿을 만들지 않는다.
  - 접미사를 직접 지정해 Spring Kafka 버전마다 다른 기본 이름에 의존하지 않는다.

### D-046. DLT 소비자는 두지 않는다 (2026-11-27)

- **결정**: DLT로 보낼 때 ERROR 로그를 남기고, 내용 확인과 재처리는 사람이 Kafka UI에서 판단한다.
- **선택지**: A. 소비자 없음 ← 선택 / B. DLT를 읽어 DB 테이블에 쌓는 소비자
- **이유**
  - DLT는 "자동으로는 처리할 수 없다"고 판정된 메시지다. 다시 자동 처리하는 경로를 만들면 같은 실패를 반복하기 쉽다.
  - B는 조회가 쉽지만 테이블과 코드가 하나씩 늘어난다. 이 프로젝트의 검증 범위 밖이다.
- **재처리 메모**: 원인을 해결한 뒤 DLT 메시지를 원래 토픽으로 다시 보내면 된다. 소비자가 멱등(D-033, D-034)이라 이미 처리된 메시지가 섞여도 안전하다.

### D-047. 예약 흐름의 비관적 락 대기는 3초로 제한한다 (D-024 후속) (2026-11-27)

- **결정**: `order.created` 처리의 재고 행 락 조회에 `jakarta.persistence.lock.timeout=3000` 힌트를 단 메서드(`findByProductIdForReservation`)를 따로 둔다. 실험 1은 타임아웃 없는 기존 메서드를 그대로 쓴다(D-017).
- **선택지**: A. JPA 힌트 ← 선택 / B. 네이티브 쿼리로 `SET LOCAL lock_timeout` 직접 실행 / C. 커넥션 단위 `lock_timeout`(모든 쿼리에 적용)
- **이유**
  - Hibernate 7.4는 PostgreSQL에서 이 힌트를 `SET LOCAL lock_timeout`으로 실행한다. 트랜잭션 안에서만 적용되고 끝나면 원래 값으로 돌아간다. 라이브러리 코드에서 확인했고, 테스트로 실제 대기 시간을 쟀다(약 3.0초 후 실패).
  - C는 락이 필요 없는 쿼리까지 영향을 받는다.
  - 3초인 이유: 키가 상품 ID라 같은 상품의 `order.created`는 한 소비자가 순서대로 처리한다. 경합은 출고 확정·예약 해제(D-048에서 API 추가. 이 결정을 적을 때는 서비스 메서드만 있었다)나 리밸런싱 중 중복 처리 정도라, 정상이면 3초를 넘길 일이 없다.
- **타임아웃 시 처리**: `PessimisticLockingFailureException`이 나고 트랜잭션은 통째로 롤백된다. 일시 장애로 보고 D-043 정책으로 재시도한다. 락이 계속 풀리지 않으면 DLT로 간다.

### D-048. 출고 확정·예약 해제 API를 추가하고, 예약 행 → 재고 행 순서로 비관적 락을 건다 (2026-11-27)

- **배경**: 흐름 5번("출고 확정 시 예약 재고 차감")은 `StockService.confirm/release`와 테스트까지만 있었고, 외부에서 호출할 진입점이 없었다.
- **결정**
  - stock-service에 `POST /reservations/{orderId}/confirm`, `POST /reservations/{orderId}/release`를 둔다. 출고를 마친 창고 시스템(WMS)이 호출하는 자리로 본다.
  - 응답: 성공 200(예약 상태 포함), 예약 없음 404, 이미 확정·해제됨 409. 에러는 order-service와 같은 ProblemDetail 형식이다.
  - 확정·해제는 예약 행과 재고 행을 비관적 락으로 잠근다(대기 상한 3초, D-047).
- **선택지**: A. 최소 API 추가 ← 선택 / B. 추가하지 않고 README에 한계로 기록
- **이유**
  - 예약과 확정을 나눈 설계(D-006)를 실행 예시로 끝까지 보여줄 수 있다.
  - 확정 결과를 order-service로 알리는 이벤트와 주문 SHIPPED 상태는 넣지 않았다. 이벤트·상태·소비자가 하나씩 늘어나 범위가 커진다.
- **락이 필요한 이유 (테스트로 확인)**
  - 기존 메서드는 락 없이 읽고 고쳤다(3단계 기준선). API로 열면 `order.created` 예약 처리와 같은 재고 행을 동시에 바꾼다.
  - 락을 뺀 상태로 `StockConfirmConcurrencyTest`를 돌리면: 같은 주문 동시 확정 16건 중 7건이 성공했고, 확정 40건과 예약 40건을 섞으면 실물 재고가 60이어야 하는데 88이었다(lost update).
  - 락을 넣으면 두 경우 모두 맞다(확정 1건만 성공, 실물 60·예약 40).
- **잠금 순서**: 예약 행 → 재고 행. 예약 처리(D-024)는 재고 행만 잠그고 예약 행은 새로 만들기만 하므로, 두 경로가 서로 반대 순서로 기다리는 교착 상태가 생기지 않는다.
- **중복 확정을 409로 둔 이유**: 같은 요청의 재시도를 200으로 받아 주는(멱등) 방식도 있다. 그러려면 엔티티의 상태 규칙을 바꿔야 해서, 이번에는 규칙을 그대로 두고 409 본문에 현재 상태를 담았다. 호출자는 "409 + 현재 상태 CONFIRMED"를 성공으로 볼 수 있다.
